# PaperLib 自动化科研知识图谱系统技术规格说明书（Technical Specification）

**项目：** HeJinlin-paperLib  
**功能名称：** Automated Research Knowledge Graph  
**文档版本：** V1.0  
**实施方式：** 分阶段开发、独立分支提交、自动化测试  
**目标：** 将 PaperLib 从论文阅读与管理工具扩展为个人科研知识管理与知识发现平台。

---

# 1. 项目背景与建设目标

## 1.1 项目背景

PaperLib 当前已经具备论文导入、解析、阅读、翻译等基础能力。

下一阶段需要实现一个自动化科研知识图谱系统，将用户个人论文库中的论文组织成具有语义关联的知识网络。

系统不应该仅仅根据论文标题、作者或关键词建立简单的论文关系，而应该深入理解论文内容，自动提取科研知识，并发现不同论文之间的关联。

例如，用户导入以下论文：

- FedAvg: Communication-Efficient Learning of Deep Networks from Decentralized Data
- FedProx: A Federated Optimization Framework for Heterogeneous Networks
- FedNova: Tackling the Objective Inconsistency Problem in Heterogeneous Federated Optimization
- Communication-Efficient Learning of Deep Networks from Decentralized Data
- 其他关于 Non-IID、客户端选择、通信效率、模型压缩的论文

系统应自动发现：

1. 这些论文都属于联邦学习相关领域。
2. FedAvg、FedProx、FedNova 是不同的联邦优化方法。
3. FedProx 针对异构客户端环境提出了相应的优化机制。
4. FedNova 研究联邦优化中的目标不一致问题。
5. 不同方法可能使用相同数据集或评价指标。
6. 某些论文可能研究相似问题，但采用不同技术路线。

这些关系应该来自论文内容，而不是仅仅依靠算法名称或关键词相似度进行猜测。

## 1.2 核心目标

实现一个能够自动构建、持续更新、交互式探索的个人科研知识图谱。

必须满足：

- 自动读取论文解析结果。
- 自动识别论文中的科研实体。
- 自动抽取实体之间的关系。
- 自动进行实体标准化和同义词归一。
- 自动发现跨论文知识关联。
- 自动构建主题聚类。
- 支持交互式图谱探索。
- 支持查看每个实体和关系的原文证据。
- 新论文导入后自动更新图谱。
- 不要求用户手工标注实体或关系。

## 1.3 非目标

第一阶段不要求：

- 构建覆盖整个互联网的全球学术知识图谱。
- 自动访问所有外部论文数据库。
- 引入复杂的分布式图数据库。
- 实现完全可靠的科研因果推理。
- 自动判断某个研究方向在整个学术界是否属于空白。
- 强制用户手工校对所有实体和关系。

系统定位是：

**基于用户个人论文库构建的、具有原文证据支撑的科研知识网络。**

# 2. 总体技术架构

## 2.1 架构原则

优先复用 PaperLib 已有技术体系，不随意引入新的基础设施。

当前项目已有 FastAPI、Python、SQLite、Vue 3 和 AI 调用接口。实施前必须重新检查当前 main 分支的实际代码，确认这些模块的真实接口和数据库结构。

建议采用以下架构：

```text
                  PaperLib
                     |
          +----------+----------+
          |                     |
       Frontend              Backend
          |                     |
   Knowledge Graph UI      FastAPI API
          |                     |
   Cytoscape.js          Knowledge Graph Service
                                |
              +-----------------+-----------------+
              |                 |                 |
        Paper Reader       AI Extractor       Entity Resolver
              |                 |                 |
        Paper Blocks       LLM Extraction      Normalization
              |                 |                 |
              +-----------------+-----------------+
                                |
                         Graph Builder
                                |
                       Evidence Validator
                                |
                         SQLite Storage
                                |
                      Graph Query Service
```

## 2.2 技术选型

| 模块 | 技术方案 | 说明 |
|---|---|---|
| 后端 | FastAPI | 沿用现有后端 |
| 数据存储 | SQLite | 第一阶段继续使用 |
| ORM/数据库访问 | 沿用现有实现 | 不引入第二套数据库访问层 |
| AI 抽取 | 复用现有 AI 调用接口 | 不重复实现模型配置 |
| 前端 | Vue 3 | 沿用现有框架 |
| 图谱可视化 | Cytoscape.js | 负责网络布局与交互 |
| 异步任务 | 沿用项目现有任务机制 | 若不存在，再设计轻量任务机制 |
| 数据校验 | Pydantic | 约束结构化输出 |
| 测试 | Pytest + 前端现有测试体系 | 兼容现有 CI |

禁止为了知识图谱功能直接引入 Neo4j、Redis、Kafka、Celery 等重量级依赖，除非有明确的性能证据和架构评审结论。

# 3. 知识图谱数据模型

这是整个系统最重要的部分。

必须先定义统一的数据 Schema，再实现 AI 抽取和前端展示。

## 3.1 节点类型

系统至少支持以下实体类型。

| 类型 | 标识 | 示例 |
|---|---|---|
| 论文 | Paper | FedAvg 原始论文 |
| 作者 | Author | H. B. McMahan |
| 研究问题 | ResearchProblem | Non-IID 数据异构 |
| 算法 | Algorithm | FedAvg、FedProx、FedNova |
| 模型架构 | Model | ResNet、MobileNetV3 |
| 数据集 | Dataset | CIFAR-10、MNIST |
| 任务 | Task | 图像分类、目标检测 |
| 评价指标 | Metric | Accuracy、F1、AUC |
| 技术概念 | Concept | Differential Privacy |
| 实验发现 | Finding | 某方法在特定条件下提升了准确率 |
| 研究领域 | ResearchArea | Federated Learning |
| 研究机构 | Institution | University / Research Lab |
| 期刊会议 | Venue | NeurIPS、ICML、CVPR |

要求：

1. 每个节点必须有唯一 ID。
2. 每个节点必须有明确的类型。
3. 每个节点应具有规范化名称。
4. 支持同义名称和别名。
5. 支持多个论文证据关联到同一个节点。
6. 不允许因为同名就直接合并不同实体。

## 3.2 关系类型

至少实现以下关系：

| 起点 | 关系 | 终点 |
|---|---|---|
| Paper | PROPOSES | Algorithm |
| Paper | ADDRESSES | ResearchProblem |
| Paper | USES | Dataset |
| Paper | USES | Model |
| Paper | USES_METRIC | Metric |
| Paper | BELONGS_TO | ResearchArea |
| Paper | AUTHORED_BY | Author |
| Paper | PUBLISHED_IN | Venue |
| Paper | REPORTS | Finding |
| Algorithm | MITIGATES | ResearchProblem |
| Algorithm | IMPROVES | Algorithm |
| Algorithm | BELONGS_TO | Concept |
| Finding | EVALUATED_ON | Dataset |
| Model | USED_FOR | Task |
| Paper | COMPARES | Algorithm |
| Paper | EXTENDS | Paper |

关系必须有方向性。

注意：

- 共同研究领域不代表方法之间存在改进关系。
- 名称相似不代表两个算法存在继承关系。
- 两篇论文使用相同数据集不代表它们直接相互引用。
- 不能根据模型常识自动生成论文没有支持的实验结论。

## 3.3 关系证据与可信度

每条关系必须关联证据。

示例：

```json
{
  "source_entity_id": "algorithm_fedprox",
  "target_entity_id": "problem_non_iid",
  "relation_type": "MITIGATES",
  "paper_id": "paper_001",
  "block_id": "block_102",
  "evidence_text": "FedProx addresses statistical and systems heterogeneity...",
  "confidence": 0.94,
  "evidence_type": "explicit",
  "verification_status": "unverified",
  "extraction_version": "1.0"
}
```

`evidence_type` 必须支持：

- `explicit`：原文直接明确表达。
- `inferred`：基于论文内容推断。
- `similarity`：语义相似关系。

前端需要使用不同的边样式区分：

- explicit：实线。
- inferred：虚线。
- similarity：点线。

每条关系都必须能查看其证据来源。

如果没有可靠证据，不允许生成确定性的科研关系。

# 4. 数据库设计

第一阶段继续使用 SQLite。

建议新增以下数据表，具体字段和类型需要根据当前项目数据库访问方式进行适配。

## 4.1 kg_entities

保存规范化实体。

```sql
CREATE TABLE kg_entities (
    id TEXT PRIMARY KEY,
    entity_type TEXT NOT NULL,
    canonical_name TEXT NOT NULL,
    normalized_name TEXT NOT NULL,
    description TEXT,
    metadata_json TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

要求：

- `id` 使用稳定唯一 ID。
- `entity_type` 使用受控枚举。
- `canonical_name` 是规范名称。
- `normalized_name` 用于匹配和去重。
- `metadata_json` 保存类型相关的附加信息。

## 4.2 kg_entity_aliases

保存实体别名。

```sql
CREATE TABLE kg_entity_aliases (
    id TEXT PRIMARY KEY,
    entity_id TEXT NOT NULL,
    alias TEXT NOT NULL,
    normalized_alias TEXT NOT NULL,
    source TEXT,
    FOREIGN KEY(entity_id) REFERENCES kg_entities(id)
);
```

例如：

```text
FedAvg
Federated Averaging
Federated Average
```

可以归属于同一个算法实体，但必须通过消歧规则确认。

## 4.3 kg_relations

保存实体之间的关系。

```sql
CREATE TABLE kg_relations (
    id TEXT PRIMARY KEY,
    source_entity_id TEXT NOT NULL,
    target_entity_id TEXT NOT NULL,
    relation_type TEXT NOT NULL,
    evidence_type TEXT NOT NULL,
    confidence REAL NOT NULL,
    status TEXT NOT NULL,
    created_at TEXT NOT NULL,
    FOREIGN KEY(source_entity_id) REFERENCES kg_entities(id),
    FOREIGN KEY(target_entity_id) REFERENCES kg_entities(id)
);
```

注意：

同一对实体可能存在不同关系，也可能有多篇论文支持同一关系。

因此，不应该仅通过 source 和 target 建立唯一约束。

## 4.4 kg_evidence

保存关系或实体的原文证据。

```sql
CREATE TABLE kg_evidence (
    id TEXT PRIMARY KEY,
    entity_id TEXT,
    relation_id TEXT,
    paper_id TEXT NOT NULL,
    block_id TEXT,
    evidence_text TEXT NOT NULL,
    section_name TEXT,
    confidence REAL,
    evidence_type TEXT NOT NULL,
    created_at TEXT NOT NULL
);
```

必须保证：

- 可以定位到具体论文。
- 可以定位到具体文本块。
- 可以展示原文上下文。
- 可以追溯抽取来源。

## 4.5 kg_extraction_jobs

保存抽取任务状态。

```sql
CREATE TABLE kg_extraction_jobs (
    id TEXT PRIMARY KEY,
    paper_id TEXT NOT NULL,
    status TEXT NOT NULL,
    stage TEXT,
    progress REAL DEFAULT 0,
    error_message TEXT,
    extraction_version TEXT NOT NULL,
    model_name TEXT,
    prompt_version TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

任务状态：

- pending
- running
- completed
- failed
- cancelled

需要支持重试和失败恢复。

## 4.6 数据库约束要求

执行者必须：

1. 提供数据库迁移脚本。
2. 不破坏旧数据库。
3. 对外键和索引进行合理设计。
4. 处理 SQLite 外键约束启用问题。
5. 为常用查询建立索引。
6. 支持旧数据升级。
7. 对数据库迁移提供测试。
8. 不能在应用启动时无条件删除或重建已有知识图谱数据。

# 5. 自动化论文知识抽取系统

## 5.1 总体流程

论文解析成功后，自动启动知识抽取任务。

```text
论文导入
   |
PDF 解析
   |
文本清洗
   |
论文结构识别
   |
章节切分
   |
实体抽取
   |
关系抽取
   |
证据验证
   |
实体标准化
   |
跨论文关联
   |
知识图谱入库
```

整个过程必须异步执行。

不能让知识图谱抽取阻塞：

- PDF 上传。
- 论文解析。
- 阅读器打开。
- 翻译任务。
- 其他用户操作。

## 5.2 输入数据

优先使用 PaperLib 已有的解析结果。

执行者需要检查现有：

- papers
- blocks
- sections
- research_log
- PDF 解析服务
- 文本清洗服务

不要重新解析 PDF，除非现有解析数据确实缺少必要信息。

抽取输入至少包括：

- 论文标题。
- 摘要。
- 章节名称。
- 章节正文。
- 文本块 ID。
- 论文 ID。
- 页码或其他可用定位信息。

优先保留章节上下文，不要简单地将全文拼成一个超长 Prompt。

## 5.3 章节识别

优先识别：

- Abstract
- Introduction
- Related Work
- Method
- Methodology
- Experiments
- Results
- Discussion
- Conclusion
- Limitations

对于章节识别失败的论文，允许回退到文本块级别抽取。

不要因为章节结构不标准而直接放弃论文。

## 5.4 实体抽取

建议按章节和文本块分批执行。

例如：

```text
论文摘要
  → 识别研究问题、主要方法、研究领域

Introduction
  → 识别研究背景、研究问题、已有方法不足

Related Work
  → 识别相关算法、已有研究和技术路线

Method
  → 识别算法、模型架构、技术细节

Experiments
  → 识别数据集、任务、评价指标、对比方法

Results
  → 识别实验发现、结果与性能比较

Conclusion
  → 识别研究贡献、结论、局限性
```

每次抽取必须返回符合 Schema 的 JSON。

不允许让模型自由输出一段自然语言后再通过不可靠的字符串解析来构建图谱。

## 5.5 建议的抽取结果 Schema

```json
{
  "paper_id": "paper_001",
  "entities": [
    {
      "name": "FedProx",
      "canonical_name": "FedProx",
      "entity_type": "Algorithm",
      "description": "A federated optimization method",
      "aliases": [],
      "evidence": {
        "block_id": "block_102",
        "text": "..."
      },
      "confidence": 0.98
    }
  ],
  "relations": [
    {
      "source": "FedProx",
      "target": "Statistical Heterogeneity",
      "relation_type": "MITIGATES",
      "evidence_type": "explicit",
      "evidence": {
        "block_id": "block_102",
        "text": "..."
      },
      "confidence": 0.94
    }
  ]
}
```

Schema 必须通过 Pydantic 验证。

模型输出存在以下情况时必须进行处理：

- JSON 格式错误。
- 实体类型非法。
- 关系类型非法。
- 证据缺失。
- block_id 不存在。
- 实体引用无法解析。
- 置信度超出范围。
- 关系端点类型不符合 Schema。

不符合规范的结果不能直接入库。

## 5.6 实体消歧和归一化

建立 Entity Resolver。

目标是将同一实体的不同表达归并。

例如：

```text
FedAvg
Federated Averaging
Federated Average
```

但不能只依赖字符串相似度。

推荐采用多级匹配：

1. 精确名称匹配。
2. 标准化名称匹配。
3. 已知别名匹配。
4. 类型约束下的语义相似匹配。
5. LLM 消歧确认。

实体归并必须考虑：

- 实体类型。
- 上下文。
- 定义。
- 所属领域。
- 论文来源。

对于存在歧义的实体，宁可暂时保留为两个节点，也不要错误合并。

实体合并需要保留别名和来源记录。

## 5.7 跨论文关系发现

抽取完成后，系统需要比较已有图谱与新论文。

重点发现：

- 相同算法。
- 相同研究问题。
- 相同数据集。
- 相同模型架构。
- 相同实验指标。
- 研究方法之间的显式改进关系。
- 研究问题与技术方案之间的关联。
- 不同研究方向之间的交叉关系。

必须区分：

**事实关系：** 论文原文明示。

**推断关系：** 根据多篇论文内容推断。

**相似关系：** 语义接近，但没有明确的技术继承或因果关系。

跨论文自动推断不能覆盖原始证据。

## 5.8 AI 调用方式

优先复用现有 AI 配置和调用接口。

执行者需要先阅读当前项目 AI 服务代码，确认：

- 模型配置。
- API 调用接口。
- 超时设置。
- 错误处理。
- Token 使用方式。
- 本地模型兼容性。

不得在知识图谱模块中另建一套独立的 API Key 配置。

抽取任务需要支持：

- 超时。
- 重试。
- 限流。
- 单篇论文失败隔离。
- 模型响应格式验证。
- 任务状态持久化。

如果模型支持结构化输出或 JSON Schema，应优先使用。

# 6. 前端知识图谱界面

## 6.1 页面入口

在 PaperLib 主界面增加独立的「知识图谱」入口。

建议页面布局：

```text
+-------------------------------------------------------+
| PaperLib                 知识图谱                     |
+-------------------------------------------------------+
| 搜索实体 | 类型过滤 | 关系过滤 | 主题 | 重建图谱       |
+-------------------------------------------------------+
|                                                       |
|                                                       |
|                  知识网络可视化                       |
|                                                       |
|                                                       |
|                                                       |
+----------------------------+--------------------------+
| 节点详情                   | 关系详情                  |
|                            |                          |
| 实体名称                   | 关系类型                  |
| 实体类型                   | 可信度                    |
| 相关论文                   | 原文证据                  |
| 实体描述                   | 定位原文                  |
+----------------------------+--------------------------+
```

界面应与 PaperLib 当前 UI 风格保持一致，不要为了知识图谱重构整个前端。

## 6.2 可视化引擎

使用 Cytoscape.js。

原因：

- 支持大规模图网络布局。
- 支持节点拖动。
- 支持缩放和平移。
- 支持节点点击。
- 支持边点击。
- 支持不同节点样式。
- 支持多种布局算法。
- 支持动态增加和删除节点。

不要自行使用 Canvas 从头实现复杂的图布局算法。

## 6.3 节点视觉设计

不同实体类型需要不同视觉区分。

例如：

| 实体 | 视觉表现 |
|---|---|
| Paper | 圆角矩形 |
| Algorithm | 圆形 |
| ResearchProblem | 六边形或菱形 |
| Dataset | 方形 |
| Model | 圆角矩形 |
| Metric | 小型圆形 |
| Concept | 菱形 |
| Finding | 特殊标记 |

节点颜色应有统一的图例。

节点大小可以根据关联数量进行适度调整，但不能让高度连接的节点无限放大。

## 6.4 交互要求

必须支持：

1. 点击节点查看详细信息。
2. 点击论文节点打开对应论文阅读器。
3. 点击关系查看原文证据。
4. 点击证据跳转对应 block。
5. 搜索实体。
6. 按实体类型过滤。
7. 按关系类型过滤。
8. 展开节点邻居。
9. 收起不需要的节点。
10. 缩放和平移。
11. 一键回到全局视图。
12. 查看关联论文列表。

## 6.5 三种视图模式

### A. 全局知识网络

显示整个论文库中的核心知识关联。

但必须限制一次渲染的节点数量。

不要把所有节点一次性塞进浏览器。

需要支持：

- 核心节点展示。
- 局部展开。
- 搜索定位。
- 邻居探索。
- 主题筛选。

### B. 主题知识地图

根据论文和实体的语义关联自动聚类。

例如：

```text
Federated Learning
    |
    +-- Optimization
    |      |
    |      +-- FedAvg
    |      +-- FedProx
    |      +-- FedNova
    |
    +-- Data Heterogeneity
    |      |
    |      +-- IID
    |      +-- Non-IID
    |
    +-- Communication Efficiency
    |
    +-- Client Selection
    |
    +-- Privacy Protection
```

主题必须来自真实论文库内容。

不能把预设主题直接伪装成自动分析结果。

### C. 单篇论文知识结构

展示一篇论文的完整研究逻辑：

```text
研究背景
   |
研究问题
   |
现有方法不足
   |
提出的方法
   |
关键技术
   |
实验设计
   |
实验结果
   |
研究结论
   |
研究局限性
```

这是一个非常重要的功能。

它能让用户不只是看到论文之间的关系，还能理解一篇论文内部的科研逻辑。

# 8. 增量更新与数据一致性

这是系统长期运行必须具备的能力。

## 8.1 新论文自动更新

新论文解析完成后：

1. 检查是否存在有效抽取结果。
2. 创建抽取任务。
3. 自动抽取实体。
4. 自动抽取关系。
5. 实体归一。
6. 生成关系证据。
7. 更新图谱。
8. 更新主题聚类。

不能每次导入新论文都重新抽取整个论文库。

## 8.2 重解析处理

当论文重新解析时：

- 旧 block_id 可能失效。
- 旧证据可能无法定位。
- 旧抽取结果可能不再适用。

因此必须支持抽取结果版本管理。

建议：

1. 保留旧抽取记录。
2. 新建新版本任务。
3. 新版本成功后再切换当前有效结果。
4. 更新相关证据。
5. 删除或失效不再有效的关系。
6. 失败时继续保留原有有效图谱。

不允许因为一次重解析失败导致整张知识图谱丢失。

## 8.3 幂等性

同一篇论文重复触发抽取，不应该生成重复节点和重复关系。

建议使用：

- paper_id
- source block
- extraction_version
- entity normalized name
- relation signature

构建幂等机制。

# 9. 性能与稳定性要求

## 9.1 后端

- 抽取任务必须异步。
- 单篇论文失败不能影响其他论文。
- 数据库写操作需要合理使用事务。
- 避免 N+1 查询。
- 高频查询建立索引。
- 对大图查询提供节点数量限制。
- 任务进度需要持久化。
- 支持服务重启后的任务恢复或安全重试。

## 9.2 前端

- 不允许默认渲染数万节点。
- 优先采用按需加载。
- 大图使用局部展开。
- 图谱查询和渲染不能阻塞主页面。
- 布局计算应避免长时间占用 UI 主线程。
- 组件卸载时清理 Cytoscape 实例和事件监听器。
- 需要处理空图谱、加载失败和部分数据缺失。

## 9.3 安全

- 不允许通过图谱 API 暴露本地文件系统路径。
- 不允许把 API Key、Token 等敏感配置返回前端。
- 论文原文必须经过现有权限和资源访问控制。
- AI 输出全部视为不可信输入。
- 不允许直接执行模型生成的 SQL 或代码。
- 模型输出必须经过 Schema 校验和业务规则校验。

## 10.4 科研语义质量测试

这是区别于普通软件功能测试的重要部分。

执行者必须准备一组固定的测试论文或模拟论文文本。

人工制定正确的预期实体和关系。

评价：

- 实体识别 Precision / Recall / F1。
- 关系识别 Precision / Recall / F1。
- 实体归一准确率。
- 证据定位准确率。
- 无证据关系比例。
- 错误实体合并率。

建议优先控制错误关系和错误合并，而不是一味追求抽取数量。

对于科研知识图谱而言，错误地将两个不同算法合并，或错误地声称某算法改进了另一个算法，比漏掉一个普通关键词更严重。

# 14. 最终产品验收场景

开发完成后，必须使用真实论文进行端到端测试。

导入 FedAvg、FedProx、FedNova 以及若干关于 Non-IID、通信效率和客户端选择的论文。

能够看到：

- 论文节点。
- 算法节点。
- 研究问题节点。
- 数据集节点。
- 模型节点。
- 指标节点。
- 论文之间的真实关联。

**第四步：查看算法关联**

- 方法介绍。

# 15. 最终设计原则

整个系统必须遵循以下五条原则：

**第一，自动化优先。**

用户负责阅读和研究，系统负责整理、抽取、关联和组织知识。

**第二，证据优先。**

每一个重要科研关系都必须能够追溯到原论文，不能只给出模型生成的结论。

**第三，准确性优先于图谱规模。**

宁可少生成一些关系，也不能生成大量虚假的科研关联。

**第四，增量化优先。**

新论文只更新必要部分，避免每次导入论文都重建整个图谱。

**第五，服务科研工作流。**

知识图谱最终应该帮助用户理解论文、比较算法、发现研究方向和形成新的科研思路，而不是仅仅提供一个漂亮的网络图。

**最终目标：让 PaperLib 成为一个能够持续理解用户个人论文库、自动积累科研知识，并辅助研究者发现知识关联的智能科研工作平台。**
